# ChaosEngine 命名与项目结构规则（结合 Godot 风格）

## 1. 目录与模块组织
- 参考 Godot 的模块化源代码组织方式，按功能将代码拆成独立模块。
- 建议目录结构：
  - `Source/ChaosEngine/`：引擎源码根目录
  - `Source/ChaosEngine/Core/`：基础类型、容器、工具类
  - `Source/ChaosEngine/Scene/`：场景、节点、对象管理
  - `Source/ChaosEngine/Rendering/`：渲染、纹理、视口、绘制任务
  - `Source/ChaosEngine/Audio/`：音频系统、播放器、通道
  - `Source/ChaosEngine/Physics/`：物理系统、碰撞、刚体
  - `Source/ChaosEngine/Platform/`：窗口、输入、平台抽象
  - `Source/ChaosEngine/Log/`：日志、输出、调试工具
- 各模块内部继续细分 `Public/` 和 `Private/`（或 `Include/` 和 `Src/`）以区分接口与实现。

## 2. 文件命名
- 采用 Godot 常见的 `snake_case` 文件名，尽量与类或功能名称一一对应。
- 例如：
  - `renderer.h` / `renderer.cpp`
  - `audio_manager.h` / `audio_manager.cpp`
  - `physics_engine.h` / `physics_engine.cpp`
  - `window.h` / `window.cpp`
- 对于内部实现文件或辅助工具，使用后缀 `_internal.h` / `_internal.cpp`：
  - `rendering_internal.h`
  - `node_internal.h`
- 头文件与源文件名一致，避免 `Class/` 前缀、双下划线或不必要的冗余。

## 3. 命名空间与模块对应
- Godot 代码更偏向于全局类型+前缀，而不是过深命名空间。
- 当前项目可保留 `chaos::` 顶级命名空间，但模块内类型名应与目录紧密对应：
  - `chaos::core::Vector`
  - `chaos::rendering::Renderer`
  - `chaos::audio::AudioManager`
  - `chaos::physics::PhysicsEngine`
  - `chaos::platform::Window`
- 若不使用多级命名空间，可将模块名作为类型前缀：
  - `ChaosRenderer`
  - `ChaosAudioManager`
  - `ChaosPhysicsEngine`

## 4. 类与结构命名
- 类名保持 PascalCase：`Renderer`、`AudioManager`、`PhysicsEngine`、`Window`。
- 结构体或 POD 类型可使用 `struct` 命名：`RenderTask`、`ViewportSize`。
- 枚举类型使用 `enum class` 并使用 PascalCase：`RenderTaskType`、`KeyState`。
- 如果需要 Godot 风格前缀，可以按类型区分：
  - `RID`、`Variant` 类似 Godot 但当前项目无需过度使用。
- 避免类名与文件名不一致。

## 5. 函数与变量命名
- Godot 风格建议：函数使用 `snake_case`，类成员使用 `_snake_case`。
- 例如：
  - `initialize()`、`register_renderer()`、`set_canvas_size()`
  - `_d2d_factory`、`_loaded_textures`、`_hwnd_render_target`
- 参数使用 `snake_case`，避免 `in_` 前缀或 PascalCase 参数名。
- 布尔变量使用 `bool` 前缀 `is_` / `has_` 或 `_enabled`：
  - `is_game_running`
  - `has_focus`
  - `_game_running`
- 常量使用 `SCREAMING_SNAKE_CASE`：`MAX_VIEWPORTS`、`DEFAULT_FPS`。

## 6. 头文件组织与包含方式
- 头文件放在 `Include/` 或 `Public/` 下，源文件放在 `Src/` 或 `Private/`。
- 头文件中避免 `using namespace`，只在 `.cpp` 中使用必要别名。
- 头文件保护使用 `#pragma once` 或传统 include guard。
- 对外接口头文件只包含最少依赖，内部实现头文件可以引用更多细节。

## 7. 第三方依赖管理
- 参考 Godot 的 `thirdparty/` 目录，把外部库集中管理。
- 建议将当前 `ChaosEngine/Dependences/ExternalLibrary/` 重构为：
  - `thirdparty/glfw/`
  - `thirdparty/openal/`
  - `thirdparty/libsndfile/`
- 自己封装第三方接口时，放在 `platform/` 或 `thirdparty/` 子目录内。

## 8. 过渡调整建议
- 将现有 `ChaosEngine/Class/` 转为 `Source/ChaosEngine/Public/` 或 `Source/ChaosEngine/Include/`。
- 将现有 `ChaosEngine/Source/` 转为 `Source/ChaosEngine/Private/` 或 `Source/ChaosEngine/Src/`。
- 逐步重命名文件：
  - `Class/graphics/Renderer.h` -> `rendering/renderer.h`
  - `Source/graphics/Renderer.cpp` -> `rendering/renderer.cpp`
  - `Class/device/Engine.h` -> `platform/window.h` / `device/engine.h`
- 推荐先统一文件名和目录，再逐步调整函数/变量命名风格。

## 9. 具体建议总结
- 目录更靠近 Godot 的模块化风格，不要把所有内容平铺在 `Class/` 下。
- 文件名改成 `snake_case`，更符合 Godot 源码习惯。
- 代码内部使用 `_snake_case` 成员名、`snake_case` 函数名。
- 保持文件名与类型对应，并通过 `Public` / `Private` 分离接口与实现。
